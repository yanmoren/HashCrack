# 压缩包修复与自动解压 — 设计文档

- 日期：2026-09-29
- 状态：待评审
- 适用范围：Windows 桌面端（主）、Android 端（远程呈现与下载）

## 1. 背景

当前 HashCrack 的流水线是 `识别文件类型 → 提取哈希 → 破解 → 显示明文密码`，到密码为止就结束了。用户拿到密码后，还得自己去找解压软件、手动输密码、手动选解压路径——**离"拖入文件 → 拿到可用结果"这个产品承诺还差最后一步**。

同时，损坏的压缩包是一个高频真实场景：网盘下载中断、存储介质坏道、传输截断都会导致压缩包结构损坏。此时用户既解不开、也修不了，而这类损坏在 ZIP 格式下是**可以程序化抢救**的。

本设计为软件增加两件事：

1. **ZIP 结构修复** —— 扫描并重建损坏的 ZIP 中央目录，产出可正常打开的压缩包
2. **破解成功后自动解压** —— 用刚破解出的密码自动解开压缩包，闭环到"拿到文件"

## 2. 已确认的需求决策

| 编号 | 决策 | 结论 |
|---|---|---|
| D1 | 功能形态 | **破解成功后自动解压**（方案 A）。修复作为解压失败时的兜底，不单独做入口 |
| D2 | 修复深度 | **ZIP 做真修复**（重建中央目录，产出可用 zip）；**7z 只做尽力解压**（结构修复不做） |
| D3 | 落盘策略 | 解压到同目录 `<包名>_解压/`；ZIP 修复额外留存 `<包名>_repaired.zip`；重名自动加 `(1)`；**默认 >2GB 的大包不留修复包**（设置里可改） |
| D4 | 手机端 | PC 端执行解压；手机端显示结果摘要 + 文件清单 + PC 路径，并支持**一键打包下载解压结果**回手机 |
| D5 | 解压引擎 | **内置 7-Zip 命令行**（`7z.exe` + `7z.dll`）到 `runtime/tools/7zip/`，不依赖用户机器 |
| D6 | 引擎可靠性 | 内置二进制是**硬性要求**：构建时缺失即构建失败；运行时并入"运行环境自检"。**明确不做运行时下载** |
| D7 | 运行时下载 | **不实现**。7-Zip 只随发布包分发，不在用户机器上联网获取（理由见 3.4） |

## 3. 能力边界（诚实性要求）

这一节是本设计的约束，不是可选建议。

### 3.1 7z 修复不做

7z 的结构信息集中在**文件末尾的头部**，且默认 solid 压缩把多个文件压成一条流，格式本身不带恢复记录。官方给出的补救办法是**手工**把完好的压缩数据块搬进一个新建的"好"归档，属人工逆向操作，无法自动完成。业界共识同样是 7z 损坏后的可修复性低于 ZIP/RAR——"没有冗余可依靠"。

因此：

- 7z 的能力是**尽力解压**：能解多少算多少，逐个报告失败文件与原因
- **不实现** 7z 的"扫描数据块 + 重建头部"实验性修复
- 产品文案上不说"修复 7z"，说"抢救式解压"

### 3.2 不假装成功

7z 头部损坏导致完全无法解压时，界面必须明确显示"7z 无冗余，头部损坏无法抢救"，**不得**用"已解压 0 个文件"之类的模糊措辞掩盖失败。

这条源自项目已知教训：早前自动策略把所有掩码硬砍 3 分钟就报"所有策略均未命中"，实际根本没跑完——**假结论比报错伤害更大**。

### 3.3 密码正确性与解压结果解耦

解压失败**绝不影响**任务的"已破解"状态。密码是对的、解压是附加产出。不能因为压缩包太烂，让用户以为密码没破出来。

### 3.4 不做运行时下载

7-Zip 二进制**只随发布包分发**，软件不在用户机器上联网获取。这是一条架构约束，不是"看情况"。

打包本身不存在障碍：官方下载页提供 "7-Zip Extra: standalone console version, 7z DLL" 独立包，当前版本 26.03，`7z.exe` + `7z.dll` 合计仅 2.4 MB。对照本项目已经把 420 MB 的 runtime（hashcat + 便携 Python + hcxtools）整体内置——如果 2.4 MB 的 7-Zip 不能打包，hashcat 早就不能了。

否决运行时下载的具体理由：

1. **违背核心卖点**。README 明确承诺"整包拷到任意 Windows 电脑双击即用，不需要安装任何运行环境"。首屏静默联网会打破这条承诺。
2. **离线与内网环境直接不可用**。而"拷贝即用"的主要受众恰恰包含内网、隔离环境机器。
3. **失败点后移，体验更差**。用户拖入文件、眼看要拿到结果时，卡在"正在下载解压工具"。
4. **杀毒软件会拦截**。程序静默联网下载可执行文件并运行，是安全软件的重点行为特征，极易被拦截甚至误报。
5. **扩大可信边界**。即便钉死 SHA-256 校验，也是把信任范围从"我们发布的安装包"扩大到"运行时网络"。

**"构建机没有 7-Zip" 这个真实场景由构建脚本解决**（见 6.3），不把风险转移到用户机上。

## 4. 架构

### 4.1 新增模块

| 模块 | 职责 | 依赖 |
|---|---|---|
| `lib/services/zip_repair_service.dart` | ZIP 结构修复：扫描本地文件头、重建中央目录与 EOCD，产出可用 zip | 仅 `dart:io`，无第三方库 |
| `lib/services/archive_extract_service.dart` | 解压执行器：调用内置 `7z.exe`，统一处理 zip / 7z，负责中文名编码、磁盘空间预检、输出解析 | `AppPaths.sevenZipExe` |
| `lib/models/archive_report.dart` | 结果模型：解压状态、文件清单、失败清单、修复产物路径 | 无 |

三个模块各自单一职责、边界清晰：修复器**只管结构与字节搬运**（不解压、不解密，加密条目原样保留）；执行器**只管调用外部工具并翻译结果**；模型**只管数据承载**。

## 5. 数据流

```
拖入 zip/7z
  → 识别文件类型（已有）
  → 提取哈希（已有）
  → 破解 → 拿到密码（已有）
  → 【新】磁盘空间预检
  → 【新】7z.exe 解压到 <包名>_解压/
       ├ 成功 ────────────────→ 记录文件清单
       └ 失败且类型为 ZIP
            → 【新】ZipRepairService 重建中央目录
            → 产出 <包名>_repaired.zip（受阈值控制）
            → 用修复产物再次解压
                 ├ 成功 → 记录文件清单 + 标注"经修复"
                 └ 失败 → 记录"救出 N 个 / M 个救不出"及原因
  → 结果卡片：密码 + 解压结果 + 打开文件夹 / 下载
```

解压阶段在 `TaskOrchestrator._run` 里紧随 `_performCracking` 之后执行，但**异常被完全隔离**：解压抛错只写入 `extractReport`，不改变 `task.status`。

## 6. 关键实现细节

### 6.1 ZIP 修复算法

**输入**：可能损坏的 zip 文件路径。**输出**：修复后的新 zip 路径 + 条目报告。

1. **先探测**：定位 EOCD（`PK\x05\x06`，从文件末尾向前最多扫描 65557 字节以兼容注释），解析中央目录。若中央目录完整且所有条目可定位，标记 `needsRepair = false`，但仍逐条校验数据区完整性。
2. **扫描本地头**：从偏移 0 起顺序查找 `PK\x03\x04`（`0x04034b50`）。
3. **解析每个候选头**：版本(2)、标志位(2)、压缩方法(2)、修改时间(2)、修改日期(2)、CRC32(4)、压缩后大小(4)、原始大小(4)、文件名长度(2)、扩展字段长度(2)，随后是文件名、扩展字段、数据。写入新包时文件名**按原字节搬运**（保留原标志位），仅在生成修复报告时按其编码（UTF-8 标志位则 UTF-8，否则 GBK）解码为可读文本。
4. **ZIP64**：若扩展字段含 `0x0001` 记录，从其中取真实的压缩后/原始大小与本地头偏移。若条目数超过 65535 或存在 >4GB 条目，中央目录写入 ZIP64 记录（`PK\x06\x06` / `PK\x06\x07`）并在 EOCD 中写 `0xFFFF`/`0xFFFFFFFF` 占位。
5. **数据描述符条目（标志位 bit 3）**：本地头中大小字段为 0，需确定数据边界：
   - 优先**精确法**：对流式 deflate 数据做增量解压，直到解压流自然结束，由解码器报告的已消费输入字节数确定真实压缩长度。仅适用于未加密条目。
   - 回退**启发式**：向后搜索最近的 `PK\x07\x08`（描述符）或 `PK\x03\x04` / `PK\x01\x02` 签名，并对候选位置做严格校验（新头能否解析出合理的文件名长度与合法压缩方法）。校验不过则丢弃该条目并记入失败清单。
6. **误命中过滤**：`压缩方法` 不在白名单（0/8/9/12/14/93/95/98/99）、`文件名长度` 或 `扩展字段长度` 越界、文件名含非法控制字符的候选，一律判定为假签名并跳过。
7. **重建中央目录**：为每个有效条目写 `PK\x01\x02` 记录（含外部属性与本地头偏移），再写 ZIP64 记录（如需）与 EOCD。
8. **流式写出**：条目数据用固定大小缓冲区（1 MB）从原文件按 `offset + length` 复制到新文件，**不得将整个压缩包读入内存**。项目已有教训：`zip2john.py` 原先 `f.read()` 整包读入，4.8 GB 的包直接撑爆内存；改用 `mmap` 后才 0.24 秒完成。

**不修改任何条目数据本身**：加密条目的密文、压缩数据、CRC 全部原样搬运，本服务不持有密码、不做解密。

**条目级容错**：单个条目损坏不中断整体修复，跳过并记录，最终报告"成功 N 条 / 放弃 M 条"。

### 6.2 解压执行器

- 命令行：`7z.exe x -p<密码> -o<输出目录> -y -bso0 -bsp1 -bb1 <压缩包>`
  - `x` 保留目录结构；`-y` 免交互；`-bso0` 屏蔽标准输出噪音；`-bb1` 输出进度供解析
- **中文文件名**：ZIP 条目名未置 UTF-8 标志位（通用目的标志 bit 11）时，该名按 GBK 解读，解压时追加 `-mcp=936`。判定依据是**标志位**而不是"先解一次看有没有乱码"——乱码无法可靠地程序化识别，猜错会静默产出乱码文件名。同一个包内允许逐条目不同编码，混合时按 UTF-8 优先、其余走 GBK。
- **进度上报**：解析 `-bb1` 输出的百分比，换算为任务进度并通过既有 `_appendLog` / 进度通道回传，避免用户面对静止界面。
- **磁盘空间预检**：解压前估算所需空间（条目原始大小之和 × 1.2），与输出盘可用空间比较；不足时直接中止并报告"还差 X GB"，不开始写入。
- **超时与取消**：复用既有进程管理方式，取消任务时终止子进程；Windows 上已有 Job Object 兜底（`windows/runner/main.cpp`），子进程不会残留。
- **输出目录命名**：`<包名>_解压`；已存在则依次尝试 `<包名>_解压(1)`、`(2)`。修复产物命名 `<包名>_repaired.zip`，同样做重名处理。

### 6.3 内置 7-Zip 的打包与自检

- 目录：`runtime/tools/7zip/`，随包分发 `7z.exe`、`7z.dll`、`License.txt`（LGPL 合规，与项目 GPLv3 兼容）
- 校验版本基准：7-Zip 26.03 (x64)
- **构建期获取**：`scripts/build_portable.py` 按顺序尝试四条来源——
  1. 项目内 `tools/7zip/`
  2. 本机已安装的 7-Zip（Windows 默认安装路径）
  3. 系统 `PATH` 中的 `7z.exe`
  4. 从官方 `7-zip.org` 下载 "7-Zip Extra" 包并**校验 SHA-256**

  前三条对绝大多数构建机已经足够；第 4 条专门解决"构建机没装 7-Zip"的场景。四条全失败则**构建失败**，不允许产出功能残缺的包。构建成功后打印内置版本号与来源（第几条命中）。
- **构建期下载的完整性校验**：期望的 SHA-256 值**硬编码在构建脚本里**并随版本更新；下载后校验不通过立即删除文件并终止构建。此校验只发生在构建机，不涉及用户机器。
- **运行期**：`AppPaths.sevenZipExe` 解析不到时，解压阶段返回明确指引（"请使用最新版安装包，或在设置中指定 7z.exe 路径"），并在"设置 → 运行环境自检"中显示可用状态与版本号。
- **不做运行时下载**（见 3.4）：应用代码中不存在任何下载 7-Zip 的路径。
- 端用户不需要自行安装任何东西：Release 包解压即用。

### 6.4 手机端下载

- 新增 `GET /api/task/<id>/extract/download?file=<相对路径>`
  - 不带 `file` 参数：将整个解压目录**流式**打包为 zip 返回
  - 带 `file` 参数：返回单个文件
  - 必须支持 `Range` 请求（断点续传），几百 MB 的传输中断后能续
  - 响应头提供 `Content-Disposition`（文件名按 RFC 5987 编码，兼容中文）
- 手机端在任务详情页显示解压状态、文件清单与"下载"按钮；PC 未运行或文件已删除时给出明确错误而非空白。

## 7. 错误处理

| 情况 | 行为 |
|---|---|
| 磁盘空间不足 | 解压前预检失败即中止，报"还差 X GB"，不产生半成品目录 |
| 密码错误 | 如实报"密码错误"，不重试、不循环 |
| ZIP 中央目录损坏 | 自动进入修复链路（本功能核心价值） |
| ZIP 修复后仍有条目救不出 | 保留成功条目，逐条列出失败条目与原因 |
| 7z 头部损坏、完全解不出 | 明确报告"7z 无冗余、头部损坏无法抢救" |
| 部分文件 CRC 校验失败 | 保留已解出的文件，列出失败文件 |
| 中文名乱码 | 加 `-mcp=936` 重试一次 |
| 源包超大（>2GB） | 不留修复包、流式解压、进度上报 |
| `7z.exe` 缺失 | 明确指引 + 设置页可指定自定义路径 |
| 输出目录已存在 | 自动加 `(1)`、`(2)`，不覆盖 |
| 手机端下载中断 | 支持 Range 续传 |
| 解压阶段任何异常 | 只写 `extractReport`，任务状态保持"已破解" |

## 8. 测试策略

### 8.1 单元测试（纯逻辑，快）

- `zip_repair_service`：
  - 完整包（无需修复，`needsRepair = false`）
  - EOCD 被截断
  - 中央目录整体删除（只剩本地头）
  - data descriptor 条目（精确法与启发式回退各一例）
  - ZIP64 条目
  - 加密条目：断言密文字节与原始包**逐字节一致**（修复不得改动数据）
  - 假签名（数据区内出现 `PK\x03\x04` 字面量）不得被误判为条目
- 命名与阈值逻辑：`_解压`、`_repaired`、重名 `(1)`、>2GB 不留修复包
- 磁盘空间预检计算
- `7z.exe` 输出解析：成功 / 密码错误 / CRC 错 / 部分失败

### 8.2 端到端测试（真实样本，单独标记，慢）

- **自造三种加密样本**：ZipCrypto、WinZip AES、7z AES（含加密头部）→ 破解 → 自动解压 → **逐字节校验解出的文件与原文件一致**
- 人为截断中央目录的 zip → 修复 → 解压 → 内容一致
- GBK 中文名 zip → 解压后文件名正确（无乱码）
- 测试样本生成方式：ZipCrypto 用 Bandizip 生成（项目已有此约定，Bandizip 产出的才是真 ZipCrypto 而非 AES）；AES 与 7z 用内置 `7z.exe` 生成

## 9. 非目标

以下明确不在本次范围内：

- 7z 的结构修复（见 3.1）
- **运行时下载或自动更新 7-Zip**（见 3.4、D7）
- RAR、AES Crypt、OpenDocument 等其他格式的修复与解压（本次只做 zip / 7z）
- 独立的"压缩包工具"入口（见 D1）
- 手机端单机解压（手机端无 `runtime`，解压只在 PC 端执行）
- 解压结果的云同步、分享链接等
- ZIP 条目的数据恢复（被覆盖或物理损坏的字节无法还原，只能跳过）

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
